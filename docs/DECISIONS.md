| 2026-07-28 | **STT/TTS provider: OpenAI** (Whisper `whisper-1` for STT, `tts-1` for TTS) via the `openai` npm SDK, configured through the existing generic `STT_TTS_PROVIDER_API_KEY` env var. | Single vendor for both directions (required by `CLAUDE.md`), a REST API/SDK shape consistent with the existing Anthropic integration (one API key, no cloud project/IAM setup), and strong English transcription quality including Indian-accented English. | 2026-07-28 | **Cost estimate (pilot scale, 50–100 interviews):** Whisper STT is $0.006/minute of audio; `tts-1` TTS is $15.00 per 1M characters (~$0.015/1K chars). | 2026-07-28 | Voice interviews require a second, explicit consent type — `voice_recording` — in addition to `data_processing`, enforced via `config.requiredConsentTypesForMode(mode)` (`backend/src/config.js`) at interview creation, and re-checked on every `POST /:id/answers/transcribe` call (not just once at creation). | Flagged as an open question back in the Phase 2 decisions log ("`docs/COMPLIANCE.md` implies more granular consent... but voice isn't built yet"). Re-checking per-call (not just at creation) satisfies `docs/COMPLIANCE.md`'s "candidate can withdraw consent" requirement: a withdrawal takes effect on the next transcription attempt, not just future interviews. |
| 2026-07-28 | Raw candidate audio is never persisted — it's held in memory only long enough to transcribe, then discarded. `responses.response_audio_url` (already in the Phase 1 schema) stays unused/null; only the resulting text transcript is stored. | DPDP data minimization (`docs/COMPLIANCE.md`): storing voice recordings would be additional biometric-adjacent personal data with no stated purpose the pilot needs — the transcript alone is sufficient for evaluation. Avoids needing blob storage infrastructure a pilot this size doesn't otherwise require. |
| 2026-07-28 | STT (`POST /:id/answers/transcribe`) is a standalone endpoint that returns the transcript for the candidate to review/edit and submit through the *existing* `POST /:id/answers` — it does not persist a response itself, and the answers-submission route/logic was not touched. | Task scope: "add voice as an alternative input/output... do not rebuild the interview logic." Coupling transcription to persistence would have required either duplicating the answer-submission logic or refactoring it into a shared helper — this keeps voice fully additive. It also means a bad transcription can be corrected before submission, and STT failures degrade gracefully (the candidate just types instead) without touching the answer flow at all. |
| 2026-07-28 | TTS calls (`GET /:id/questions/:questionId/audio`) are synthesized on every request rather than cached/stored. | Pilot-scale traffic (50–100 interviews, a handful of question plays each) makes the extra ~$1 in repeat TTS calls cheaper than building caching infrastructure — matches `CLAUDE.md`'s "no premature complexity." Revisit if usage or cost grows. |
| 2026-07-28 | The OpenAI client in `backend/src/services/voiceService.js` is constructed lazily (on first use) rather than at module load time. | The `openai` SDK throws immediately if `apiKey` is empty/undefined at construction (unlike `@anthropic-ai/sdk`, which only errors when a call is made). Eager construction broke every test suite that imports `app.js` (which requires `interviewRoutes.js` → `voiceService.js`) in environments without `STT_TTS_PROVIDER_API_KEY` set — including CI and local dev before a key is configured. Lazy init defers the error to when a voice feature is actually invoked. |
| 2026-07-28 | The interview `mode` ("Text" / "Voice") is chosen by the candidate on the setup screen (`frontend/pages/index.js`) and applies to the whole interview session — there's no per-question mode switching. | The Phase 1 schema already models `mode` as an interview-level field (not per-question), and Phase 3's setup screen had hardcoded `mode: 'TEXT'`. | 2026-07-28 | Credit deduction is an **atomic conditional decrement** (`organization.updateMany({ where: { id, creditBalance: { gt: 0 } } })`) inside the same Prisma `$transaction` as the interview + question creation, not a read-balance-then-write. | Avoids a TOCTOU race where two concurrent interview-creation requests both read a balance of 1 and both proceed, sending the balance negative — the conditional `WHERE` clause guarantees only one concurrent deduction can succeed when the balance is exactly 1. The interview row and its `credit_transactions` row are created in the same transaction as the deduction, so a lost race rolls back the interview too (`backend/src/routes/interviewRoutes.js`, `backend/src/services/creditService.js`). |
| 2026-07-28 | The credit balance is checked twice: an early non-atomic read (fail fast, before the Claude API call) and the atomic conditional decrement (authoritative, at interview-creation time). | Avoids paying for/waiting on a question-generation LLM call when the organization obviously has 0 credits, while still relying only on the atomic check for correctness (the early check is purely an optimization, not a security boundary). |
