| 2026-07-28 | Chose **Prisma** as the migration tool over `node-pg-migrate`. | Backend stack is Node.js/Express; Prisma gives a single-source-of-truth schema (`schema.prisma`), generates SQL migrations automatically, and has a typed client ready for when API routes are built in a later phase — fits the "keep it simple" pilot-scale approach better than hand-writing migrations with `node-pg-migrate`. |
| 2026-07-28 | The Phase 1 migration (`backend/prisma/migrations/20260728000000_init/migration.sql`) was authored by hand rather than generated via `prisma migrate dev`. | No live `DATABASE_URL` is available in this environment yet (Postgres instance not provisioned). SQL was written to match what Prisma would generate from `schema.prisma`; run `npx prisma migrate dev` against a real database in Phase 1's follow-up (or start of Phase 2) to confirm it applies cleanly and regenerate if Prisma's output differs. |
| 2026-07-28 | Row IDs use Prisma's app-generated `uuid()` default rather than a Postgres-native `gen_random_uuid()`. | Avoids requiring the `pgcrypto`/`uuid-ossp` extension on the managed Postgres instance (Supabase/Railway) — one less thing to provision at pilot scale. |
| 2026-07-28 | `evaluations` is one row per interview (not per response), with a `scorecard` JSON column for per-question/criterion detail rather than a separate table. | Matches the "structured feedback report" requirement in `CLAUDE.md` without adding a table before we know the report's real shape; simplest option for pilot scale. Revisit if per-criterion querying/reporting is needed later. |
| 2026-07-28 | Default LLM model is `claude-opus-5` (configurable via `ANTHROPIC_MODEL`). | No model was specified for the project. Opus 5 is the strongest available model for the JD/resume question-generation and transcript-evaluation quality this feature is graded on. Given the pilot's cost sensitivity (`CLAUDE.md`: "no over-provisioning"), this is easy to downgrade to `claude-sonnet-5` via env var if per-interview cost becomes a concern at higher volume — logged here so that tradeoff is visible, not silent. |
| 2026-07-28 | Both LLM calls (question generation, evaluation) use structured output (`output_config.format` with a Zod schema via `client.messages.parse()`), not tool use or free-text parsing. | Guarantees schema-conforming JSON or a clear parse failure — avoids ad hoc regex/JSON.parse on free text. A failed/refused response surfaces as an HTTP 502 rather than getting silently stored as malformed data. |
| 2026-07-28 | LLM calls run with default (adaptive) thinking and `effort: "medium"`, not `thinking: {type: "disabled"}`. | Disabling thinking on Claude Opus 5 has two known failure modes (tool-call-as-plain-text, `<thinking>` tag leakage into output) that are more likely to corrupt structured JSON output than adaptive thinking's small latency cost. Medium effort balances quality and per-request latency for a synchronous HTTP flow. |
| 2026-07-28 | DPDP consent is a single required type, `data_processing`, checked in `backend/src/config.js` (`REQUIRED_CONSENT_TYPES`). | `docs/COMPLIANCE.md` implies more granular consent (e.g. separate `recording` consent for voice) but voice isn't built yet (Phase 4). One type keeps the Phase 2 API surface minimal; the schema (`consent_records.consent_type` is a free string) already supports adding more types later without a migration. |
| 2026-07-28 | Backend npm dependencies were installed with `npm install` in this environment (network available), and `npx prisma generate` was run manually because npm's install-script gate (`allow-scripts`) blocked Prisma's automatic postinstall generation step. | Needed a working `@prisma/client` to write and run the Phase 2 test suite. Anyone cloning the repo fresh should run `npm install && npx prisma generate` in `backend/` (or approve the scripts via `npm approve-scripts`) if they hit the same gate. |
| 2026-07-28 | Added two read-only endpoints not in the original Phase 2 API — `GET /api/interviews` and `GET /api/interviews/:id` (`backend/src/routes/interviewRoutes.js`) — during Phase 3, which was scoped as "UI only, no new backend logic." | The reviewer dashboard (list interviews, view transcript + evaluation) and the candidate interview screen's refresh-recovery both need to read interview state, and no such endpoint existed. Confirmed with the user before adding; kept intentionally minimal (Prisma reads only, no new write paths, no LLM calls, no new audit-log actions since nothing AI-related happens on a read) rather than expanding scope further. |
| 2026-07-28 | Phase 3 frontend is a hand-written Next.js 14 (Pages Router) + Tailwind 3 app in `frontend/`, plain JS (no TypeScript), rather than scaffolded via `create-next-app`. | Matches `CLAUDE.md`'s stated stack (React/Next.js, Tailwind) and the backend's plain-JS convention; hand-writing avoids an interactive scaffolding step and keeps the dependency set minimal for pilot scale. |
| 2026-07-28 | The candidate "consent screen" (`frontend/pages/index.js`) also collects job title, JD text, and resume text, and creates the interview (`POST /api/interviews`) immediately after consent is recorded, rather than being a separate step. | `CLAUDE.md`'s Phase 3 prompt lists three screens (consent -> interview -> completion) but the interview-creation API requires JD + resume text that no other screen was specified to collect, and there's no recruiter/admin portal yet to pre-populate it. Revisit once a recruiter-facing interview-setup flow exists. |
